Token Optimization
RTK and Headroom operate at different layers. RTK filters shell command output. Headroom compresses LLM conversation context. Use both together.
5 practices
P01
RTK works automatically via the Claude Code hook — never manually
RTK · Always On

RTK is wired into Claude Code as a PreToolUse hook in ~/.claude/settings.json. Every Bash command Claude runs is automatically intercepted and rewritten to rtk <command>. You do not prefix commands yourself.

# What the hook does silently: # git status → rtk git status # npm install → rtk npm install # ls -la → rtk ls -la # Check your savings any time: rtk gain # overall summary rtk gain --history # per-command breakdown rtk session # adoption rate per session

The only commands you run yourself are analytics (rtk gain, rtk discover, rtk session) and debug commands (rtk verify).

P02
The hook config in settings.json is what activates RTK
RTK · Configuration

Installing RTK is not enough. Without the PreToolUse hook in settings.json, RTK is installed but completely idle. The hook is the activation step — verify it first whenever savings look wrong.

# ~/.claude/settings.json { "hooks": { "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "rtk hook claude" }] }] }, "autoUpdatesChannel": "latest", "extraKnownMarketplaces": { ... headroom config ... } }

Restart Claude Code after any change to settings.json — hooks are loaded at startup.

P03
Start Headroom proxy before every Claude session
Headroom · Critical

Headroom is not a background service. It must be manually started each session before launching Claude Code. Forgetting this is the root cause of every Connection Refused error we've hit.

# Terminal 1 — keep this open the whole session headroom proxy # Terminal 2 — your working terminal $env:ANTHROPIC_BASE_URL = "http://localhost:8787" claude # Or both in one command: headroom wrap claude
Quick confirm: curl http://localhost:8787/health — if you get JSON, proxy is up. If Connection Refused, it's not started yet.
P04
Make ANTHROPIC_BASE_URL permanent in PowerShell profile
Headroom · Setup

Setting $env:ANTHROPIC_BASE_URL in a terminal only lasts that session. Add it to your PowerShell profile so it's always present — then you only need to start the proxy, not re-set the variable each time.

# Open your PowerShell profile: notepad $PROFILE # Add this line and save: $env:ANTHROPIC_BASE_URL = "http://localhost:8787" # Verify it's set in a new terminal: echo $env:ANTHROPIC_BASE_URL # Expected: http://localhost:8787
Important: If you add this to your profile but forget to start the proxy, every Claude Code launch will fail with Connection Refused. Start proxy first, always.
P05
Verify both tools are actively saving tokens — don't assume
Both Tools · Verification

Both RTK and Headroom can appear working while silently doing nothing — a missing hook, an unset env var, a stopped proxy. Check savings at the start of important sessions.

# RTK — verify savings rtk gain # Tokens saved: 49.8K (89.9%) # If 0 → hook is not active rtk discover # Find missed opportunities
# Headroom — verify savings curl http://localhost:8787/stats # tokens_saved_total should increase # If 0 → ANTHROPIC_BASE_URL not set # or proxy not running

Context Files — QA_PIPELINE.md & DB_VALIDATION.md
Two files carry all the context needed across every session. Understanding each file's role is how you avoid repeating yourself to Claude.
3 practices
P06
QA_PIPELINE.md is the only file you change between sessions
Context · QA_PIPELINE

QA_PIPELINE.md has one CONFIG block at the top. That is the only part that changes between modules. The rest — phases, steps, agent instructions, output format — stays exactly the same every time.

# QA_PIPELINE.md — change ONLY this block ``` TARGET_MODULE : Data Centre ← only this APP_URL : https://portal... ← stays same ENVIRONMENT : QAN ← stays same FULL_USER : statususer ← stays same FULL_PASSWORD : Password#1 ← stays same RESTRICTED_USER : <restricted> ← per-module ```

Switching from DataCentre to ProviderTariff takes one line change. No re-explaining the methodology, no re-writing instructions. Claude reads the file and knows the full pipeline.

P07
DB_VALIDATION.md is for Phase 2 onwards — planner doesn't need it
Context · DB_VALIDATION

DB_VALIDATION.md stores the verified schema, column names, and reusable SQL queries for each module. The planner agent (Phase 1) discovers structure live from the UI — it does not need this file. The generator and test scripts (Phase 2+) reference it for DB assertions.

# What DB_VALIDATION.md provides: # - oncilla schema: user, userPermission, # dataCentreDefinition, ipPool, etc. # - Column names verified against live DB # - Connection helper pattern (dbUtils.js) # - Status values: 'active'|'inactive'|'deleted' # (NOT 'state' — that was a real bug we caught) # .env keys used by DB scripts: QA_DB_HOST, QA_DB_USER, QA_DB_PASSWORD, QA_DB_NAME
Why it exists: Without DB_VALIDATION.md, Claude would have to re-discover column names and table structure each session — and risk using wrong column names that silently pass queries but return wrong data.
P08
Compress context files when they grow — without losing behavior
Context · Optimization

QA_PIPELINE.md grew through iteration — sections added over multiple sessions. We used a structured refactoring instruction to compress it without losing a single rule or workflow. Use the same pattern when any context file becomes bulky.

# Paste before the file when asking Claude to compress: Treat this as a refactoring exercise, not a rewrite. Remove duplicated instructions, merge overlapping sections, compress verbose wording. Replace repeated paragraphs with reusable rules. Before returning: verify no rule was removed, no capability lost, no workflow changed, no output format changed.
When to do it: When QA_PIPELINE.md or DB_VALIDATION.md has grown through repeated additions and sections feel repetitive. Smaller context files = fewer tokens consumed every time Claude reads them.

Prompt Practices
How you phrase instructions and constraints in QA_PIPELINE.md directly determines output quality across every module.
2 practices
P09
Pair "you must" rules with explicit "you must not" rules
Prompt · Constraints

QA_PIPELINE.md uses both patterns throughout. Positive rules tell Claude what to do. Negative rules prevent reasonable-looking shortcuts that break your intent — especially critical in exploratory testing where "close enough" is a failure.

# Positive rule — what to do: You must click every reachable menu. You must interact with all forms. # Negative rule — what to avoid: You must not skip sections. You must not ignore disabled fields. You must not stop after happy-path. You must not assume functionality without evidence from the live UI.

When you add new business logic to QA_PIPELINE.md, pair every new must with a corresponding must not for the likely shortcut.

P10
Add business rules to QA_PIPELINE.md as explicit sections, not prose
Prompt · Structure

Business logic like status transition rules, billing validation, and dialog behavior was added to QA_PIPELINE.md as numbered sections with explicit states — not as conversational descriptions. Claude follows structured rules more reliably than paragraphs.

Do this (structured)
✓ setup → requested: needs Update permission
✓ setup → active: needs Approver or Admin
✓ setup → deleted: needs Admin
✓ Dialog: "Are you sure you want to change…"
Avoid (prose)
✗ "Users can change status depending on their role and the current state of the record…"
✗ Mixing multiple rules into one sentence

MCP Agents
Three agents, three phases. Picking the wrong one for the wrong phase wastes the whole session.
2 practices
P11
Use the right agent for each phase — in order
MCP · Agent Sequence

Phase sequence

1
playwright-test-planner
Navigates live app with FULL_USER, discovers all UI elements, saves test plan. Must run first — generator reads its output.
2
playwright-test-generator
Reads the saved plan, executes each step in browser, writes test files. Only invoke after planner has saved the plan.
3
playwright-test-healer
Runs failing tests, reads error output, fixes locators and assertions. Only invoke after tests have been run and failed.

Common mistakes

Never do these
✗ Running generator before planner saves the plan
✗ Using RESTRICTED_USER for Phase 1 — create button and other controlled elements stay hidden
✗ Invoking healer without running tests first
✗ Running planner without confirming all permissions are active in DB
P12
Phase 1 requires all capabilities active — verify in DB first
MCP · Permissions

If any capability is missing for the target module when the planner runs, that UI element is hidden — the planner can't discover or generate scenarios for it. Always check permissions in DB before starting Phase 1.

# DB check before Phase 1 — verify all active SELECT title, status FROM oncilla.userPermission WHERE username = 'statususer' AND title LIKE 'capabilityDataCentre%'; # All rows must show status = 'active' # Use DB_VALIDATION.md for correct column names
  • Negative permission tests use a RESTRICTED_USER — a separate account or same account with capabilities temporarily set to inactive in DB
  • Status column in oncilla.userPermission is status, not state — DB_VALIDATION.md has the verified column names
P13
If MCP shows Disconnected — check proxy, then reload VSCode
MCP · Troubleshooting

When the headroom MCP server shows Disconnected in VSCode, the most likely cause is the proxy not running — not a config problem.

# Step 1: Start the proxy if not running headroom proxy # Step 2: Reload VSCode window to force reconnect # Ctrl+Shift+P → Developer: Reload Window # Step 3: If still disconnected, check mcp.json env: # .vscode/mcp.json → "headroom" server must have: # "env": { "HEADROOM_PROXY_URL": "http://127.0.0.1:8787" }

Session Reliability
A fast diagnostic habit cuts hours of lost time from connection errors to minutes. Always follow the same startup order.
3 practices
P14
Always follow the same 4-step startup sequence
Session · Reliability

Connection Refused appeared multiple times because the startup sequence was wrong or skipped. Following the same order every session prevents it entirely.

1
Start Headroom proxy — headroom proxy in a dedicated terminal. Wait for "Uvicorn running on http://127.0.0.1:8787"
2
Confirm proxy health — curl http://localhost:8787/health returns JSON
3
Open working terminal — confirm $env:ANTHROPIC_BASE_URL is set to http://localhost:8787
4
Launch Claude Code — claude. Use claude auth status if auth is in doubt
P15
Use a diagnostic sequence for API errors — don't guess
Session · Troubleshooting

When Claude shows Unable to connect to API, run these checks in order. Stop when you find the cause. Don't reinstall, don't restart VSCode first.

# Step 1: Is the proxy running? curl http://localhost:8787/health # Step 2: Is the env var set? echo $env:ANTHROPIC_BASE_URL # Step 3: Is Claude authenticated? claude auth status # Step 4: Can you reach Anthropic directly? curl -I https://api.anthropic.com # Step 5: Verbose output claude --debug "Hello"
P16
Proxy problems and auth problems look identical — check proxy first
Session · Diagnosis

Both produce "Unable to connect to API" but have completely different fixes. Misdiagnosing costs significant time. Based on our history, proxy problems are far more frequent.

Proxy problem (most common)
• Error on any Claude command, immediately
• curl localhost:8787/health → Connection Refused
• Fix: headroom proxy in a new terminal
Auth problem (less common)
• Error persists even without Headroom proxy
• claude auth status shows not logged in
• Fix: claude auth logout then claude auth login

Workflow & Output Quality
Practices for consistent, high-quality outputs — especially in long sessions and when Claude stalls mid-response.
3 practices
P17
Scope work to one module at a time
Workflow · Scoping

Asking Claude to generate test cases across multiple modules at once leads to stalls, incomplete outputs, and poor coverage. One module per session produces better, more complete results — and uses fewer tokens per session. This is exactly what the TARGET_MODULE config block in QA_PIPELINE.md enforces.

# Each session, change only this line: TARGET_MODULE : ProviderTariff TARGET_MODULE : DataCentre TARGET_MODULE : Transactions TARGET_MODULE : IPPool

The methodology in QA_PIPELINE.md is module-agnostic. Only the target changes.

P18
Use "continue" for stalled mid-stream responses
Workflow · Recovery

When Claude shows Response stalled mid-stream. The response above may be incomplete, just reply continue. Claude holds the full context — it resumes exactly where it stopped without reprocessing the whole instruction set.

# Claude stalled mid-response? Your next message: continue # If it stalls again on a very large task: Let's try it for one feature and see how it behaves. # Never re-send the full prompt — that resets the context # and burns the tokens you already spent
P19
Always validate UI → API → DB — not just what the screen shows
Workflow · Validation Depth

Every significant action is validated at three layers — UI state, API response, DB record. Validating only the UI catches around 40% of real bugs. DB_VALIDATION.md provides the schema and queries so three-layer validation doesn't require new queries each session.

UI
Toast message, table refresh, field state — what the user sees
API
Response status, schema, payload values — what the backend returned
DB
SQL query confirms record exists, status updated, timestamps correct — using verified column names from DB_VALIDATION.md
